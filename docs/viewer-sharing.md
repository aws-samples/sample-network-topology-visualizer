# 화면 공유 경로 — 보안 검토자용 안내

이 문서는 수집기가 만든 네트워크 다이어그램 화면(`index.html`)을 **사람에게 보여 주는 길 다섯 가지**를 보안 검토자 관점에서
정리합니다. 길마다 「누가 열 수 있나 · 누가 열었는지 남나 · 어떻게 거둬들이나 · 얼마나 사나 · 주소가 어디에 남나」를 적고,
근거가 되는 템플릿 파일을 함께 적습니다.

- **제품이 제공하는 길**은 1~3번입니다(스택 A 기본 출력 · S3 서명 URL · 스택 C). 4·5번은 **고객이 자기 계정에 직접 구성하는
  길**이고 제품 템플릿에는 없습니다. 4·5번에 적은 구성은 제품 쪽에서 **검증하지 않았습니다**(§7).
- AWS 서비스 자체의 성질(서명 URL 최대 수명 등)은 AWS 공식 문서 기준이고, 그렇게 표시했습니다.
- 각 스택이 만드는 IAM 권한은 [필요한 IAM 권한](required-permissions.md)에 있습니다.

## 0. 먼저 — 화면 파일 하나에 무엇이 들어 있나 (다섯 길 공통)

보안 검토의 대상은 「링크」보다 **파일**입니다. 어느 길로 열든 사람 손에 들어가는 것은 같은 `index.html` 입니다.

1. **네트워크 구성 자체.** 계정 ID · CIDR · 공인 IP · 연결 구조가 화면 파일 안에 들어 있습니다.
   파일을 한 번 받은 사람은 그 내용을 **영구히** 갖습니다. 아래 어느 길의 「회수」도 이미 받은 파일을 지우지 못합니다.
2. **실시간 모니터링을 켠 스택이면, 서명된 S3 주소 4개.** 서명 함수가 5분마다, 그리고 구조 수집이 성공한 직후에 화면 파일의
   주소 칸을 새로 채워 게시합니다(`infra/stack-a-collector.yaml` 의 서명 함수 · `infra/state-lambda/signer.py`).
   - 상태 읽기 `GET state-latest.json`
   - 모니터링 켜기 · 끄기 신호 쓰기 `PUT control/desired.json`
   - 모니터링 켜기 · 끄기 신호 읽기 `GET control/desired.json` — 켜 둔 창이 1분마다 읽어, 다른 창이 켜거나 바꾸거나 끈 것을 따라갑니다
     (2026-10-28 · 「따라 보기」)
   - 최신 화면 열기 `GET index.html` — 사람이 «최신 화면 열기» 를 누를 때만 쓰는 이동 주소
   - 네 주소의 서명자는 **서명 함수 역할**(`SignerRole`)입니다. S3 는 서명 URL 요청을 서명한 주체의 권한으로 판정하므로,
     이 주소로 할 수 있는 일은 그 역할의 권한(키 세 개 — 신호 읽기는 이미 있던 그 키의 읽기 권한)을 넘지 않습니다.
   - 수명 = 12시간과 서명 함수 자격 증명의 남은 수명 중 짧은 쪽입니다.
3. **모니터링이 없는 스택이면** 주소 칸이 비어 있고 화면의 CSP `connect-src` 가 `'none'` 입니다. 파일 밖으로 나가는 요청이 0 이고
   서명 주소도 0 입니다.

**사용자가 겪는 일로 바꾸면**: 모니터링을 켠 스택에서 화면 파일을 전달받은 사람은, 파일을 받은 뒤 최대 약 12시간 동안
(1) 가장 최근 상태 숫자를 볼 수 있고, (2) 모니터링을 켜거나 끌 수 있고, (3) 그 시점의 최신 화면으로 넘어갈 수 있습니다.
같은 스택의 화면을 여러 창이 열어 두면, 마지막으로 켜거나 바꾼 창의 설정을 다른 창들이 따라 봅니다(어느 창에서 끄든 모두 꺼집니다).
켜기에는 비용이 따르므로 상한이 두 겹입니다. 화면은 켠 시각부터 **켤 때 고른 시간**(30분 · 1시간 · 2시간 · 4시간 · 8시간, 기본 4시간)까지만 모니터링을 켜 두고, 창을 닫으면 연장이
끊겨 약 20분 안에 멈춥니다(`renderer/flow.js`). 서버(상태 함수)는 화면과 무관하게 **마지막 켜기 · 끄기 신호 쓰기 + 8시간**이 지나면
스스로 멈춥니다(`infra/state-lambda/handler.py`) — 조작된 화면이 끝없이 켜 두는 것을 막는 천장입니다.
12시간이 지나면 그림은 그대로 남고 숫자만 멈춥니다.

## 2. 길마다

### ① S3 에서 내려받기 — 스택 A 의 기본 출력

- **무엇**: 관리자가 `aws s3 cp` 로 `index.html` 을 받아 엽니다. 스택 A 가 그 명령을 출력값으로 줍니다.
  버킷은 공개 차단 4항목 전부 · 저장 암호화 · 평문 전송 거부이고, 공개 주소가 없습니다(`infra/stack-a-collector.yaml` 의 `ArtifactBucket`).
- **누가 열 수 있나**: 버킷 정책은 사람(주체)을 좁히지 않습니다 — 정책 문장은 평문 거부와 CloudFront 허용 둘뿐입니다.
  그래서 **모니터링 계정 안에서 그 버킷을 읽을 IAM 권한이 있는 누구나** 받을 수 있습니다.
  계정에 넓은 읽기 권한(예: AWS 관리형 `ReadOnlyAccess`, S3 읽기 포함)을 받은 사람이 있다면 그 사람도 포함됩니다.
- **누가 열었는지**: 스택 A · B · C 어느 템플릿도 CloudTrail 추적이나 S3 서버 액세스 로그를 만들지 않습니다. 내려받기(`GetObject`)는
  CloudTrail **데이터 이벤트**이고 기본으로 기록되지 않습니다(AWS 문서 기준). 고객이 그 버킷에 데이터 이벤트를 켜면 **받은 사람의
  이름**이 남습니다. 받은 뒤 파일을 누구에게 넘겼는지는 어디에도 남지 않습니다.
- **거둬들이기**: IAM 권한을 빼면 **앞으로** 못 받습니다. 이미 받은 파일은 회수할 수 없습니다. 파일 안의 서명 주소는 최대 약 12시간 뒤
  스스로 무효가 됩니다(§0).
- **수명**: 파일 내용은 영구. 실시간 숫자는 받은 시점부터 최대 약 12시간.
- **주소가 남는 곳**: 주소가 없습니다. 대신 파일이 PC · 메일 · 메신저에 남습니다.
- **맞는 경우**: 보는 사람이 몇 명의 관리자뿐이고, 그 사람들이 이미 모니터링 계정에 로그인할 수 있을 때.

### ② S3 서명 URL — 기본 경로 (스택 C 없이)

두 가지가 있습니다.

- **(가) 화면 안에 이미 들어 있는 주소** — §0 의 세 주소. 사람이 따로 발급하지 않습니다. 「최신 화면 열기」 주소는 상태 주소와
  **같은 오리진의 `/index.html`** 일 때만 화면이 버튼을 냅니다. 즉 ① 로 받은 파일을 전달하면 이 주소도 같이 갑니다.
- **(나) 관리자가 따로 발급하는 링크** — 관리자가 자기 자격 증명으로 `index.html` 의 서명 URL 을 만들어 보냅니다. 설치 안내서에는
  이 절차가 없고 제품 쪽에서 **검증하지 않았습니다.** 받은 사람의 브라우저에서 화면은 버킷 오리진(`https://<버킷>.s3.<리전>.amazonaws.com`)
  에서 열리고, 화면의 `connect-src` 도 같은 오리진이라 실시간 숫자가 같은 오리진 요청으로 동작할 것으로 **코드상 추론**합니다.
  주소의 호스트가 리전 엔드포인트 · 가상 호스트 모양이 아니면(예: 전역 엔드포인트) 오리진이 달라져 CORS 에 걸릴 수 있습니다 —
  서명 함수가 같은 이유로 리전 엔드포인트를 고정합니다.
- **누가 열 수 있나**: 주소를 가진 누구나. 로그인이 없습니다. 서명 URL 은 「가진 사람이 곧 주인」인 토큰입니다(AWS 문서 기준).
- **누가 열었는지**: 요청은 **서명한 주체의 권한**으로 처리됩니다. 데이터 이벤트를 켜도 남는 이름은 (가) 는 서명 함수 역할,
  (나) 는 발급한 관리자이고, 실제로 연 사람은 **요청 IP** 로만 보입니다.
- **거둬들이기**: 주소 하나만 끊는 기능은 없습니다. 서명에 쓴 자격 증명이 끊기면(세션 회수 · 삭제 · 비활성) 그 자격 증명으로 서명한
  주소가 **전부** 무효가 됩니다(AWS 문서 기준). 서명 주체의 권한을 빼도 같은 효과입니다. (가) 를 이렇게 끊으면 모든 사람의
  실시간 숫자가 같이 멈춥니다.
- **수명**(AWS 문서 기준): CLI · SDK 최대 7일, 콘솔 1분~12시간. **임시 자격 증명**(역할 · Identity Center 로그인)으로 서명하면 지정한
  수명과 상관없이 **그 세션이 끝날 때** 무효가 됩니다. 7일 링크는 장기 액세스 키가 있어야 하는데, 설치 안내서는 장기 키를 만들지
  않도록 합니다.
- **주소가 남는 곳**: 메신저 · 메일 · 브라우저 기록 · 고객이 켰다면 S3 서버 액세스 로그(요청 주소 전체가 남습니다 — AWS 문서 기준).
  스택 A 는 서버 액세스 로그를 켜지 않습니다. 메신저의 링크 미리보기 봇이 주소를 대신 열 수 있습니다(일반 주의).
- **맞는 경우**: AWS 계정이 없는 사람에게 **몇 시간만** 보여 줄 때.

### ③ 스택 C CloudFront 서명 링크 — 선택

- **무엇**: CloudFront 가 비공개 버킷의 `index.html` **한 키만** 읽기 전용으로 내줍니다. 버킷 정책이 같은 계정 CloudFront 배포에
  `index.html` 읽기만 허용하고, 배포는 GET · HEAD 만 받고 캐시하지 않으며 서명 없는 요청은 403, https 만 받습니다
  (`infra/stack-c-viewer.yaml`). 링크는 관리자 PC 의 `openssl` 로 만듭니다(`infra/issue-viewer-link.sh`).
- **누가 열 수 있나**: 링크를 가진 누구나. 로그인 없음. 링크가 여는 경로는 `/index.html` 하나입니다.
  검증 결과: 서명 없음 · 만료 · 다른 경로 · 변조 · 쓰기 요청은 403, S3 직접 접근도 403.
- **누가 열었는지**: **사람을 식별하지 못합니다.** 설계에서 받아들인 대가입니다. 액세스 로그에 남는 것은 요청 IP · 시각 · 브라우저
  정보이고, 쿠키는 기록하지 않습니다.
- **거둬들이기**: 키 교체로 그 키로 서명한 링크를 모두 무효로 합니다. 링크 하나만 끊는 방법은 없습니다. 교체 방식은 §4 에 있습니다.
- **수명**: 관리자가 정합니다. 스크립트는 기본값 없이 일수를 반드시 받으며 상한을 두지 않습니다.
- **주소가 남는 곳**:
  - **CloudFront 액세스 로그에 서명 포함 링크 전체가 남습니다.** 기본 보존 90일(`AccessLogRetentionDays`). 로그 버킷 정책이
    계정 루트와 `LogReaderPrincipalArns` 에 적은 역할 · 사용자 외의 읽기를 거부합니다. 감사 담당이 로그를 봐야 하면 그 역할을
    여기에 적습니다.
  - 메신저 · 메일 · 브라우저 기록 · 링크 미리보기 봇(일반 주의).
  - 리퍼러로는 새지 않습니다 — 응답에 `Referrer-Policy: no-referrer`, 검색 노출 차단 `X-Robots-Tag` 가 붙습니다.
- **맞는 경우**: AWS 계정이 없는 사람에게 **오래** 보여 주고, 누가 봤는지는 몰라도 되는 팀.

### ④ Identity Center 권한 세트로 S3 직접 열람 — 고객 구성 · 제품 밖

- **무엇**: 고객이 모니터링 계정에 「이 버킷의 `index.html` 읽기만」 주는 권한 세트를 만들어 보는 사람들에게 할당합니다.
  예: `s3:GetObject` on `arn:aws:s3:::<버킷>/index.html`. 보는 사람은 자기 로그인으로 ① 처럼 `aws s3 cp` 하거나, S3 콘솔에서 엽니다
  (콘솔은 그 사람 세션으로 서명 URL 을 만듭니다 — AWS 동작, 제품 쪽 미검증).
- **누가 열 수 있나**: 권한 세트를 할당받은 사내 사용자. 다만 버킷 정책이 주체를 좁히지 않으므로 이 권한 세트가 **유일한** 길이
  되지는 않습니다 — 이미 넓은 S3 읽기 권한을 가진 사람은 여전히 받을 수 있습니다.
- **누가 열었는지**: 다섯 길 가운데 **사람 이름이 남는 유일한 길**입니다 — 단, 고객이 이 버킷에 CloudTrail S3 데이터 이벤트를 켰을
  때만(AWS 문서 기준, 데이터 이벤트는 요금이 따로 붙습니다). 화면을 연 뒤의 실시간 요청은 여전히 서명 함수 역할로 남습니다(§0).
- **거둬들이기**: 할당을 해제하면 다음 요청부터 막힙니다. 받은 파일은 회수 불가.
- **수명**: 로그인 세션(권한 세트 설정 1~12시간). 받은 파일은 영구.
- **맞는 경우**: 보는 사람 전원이 사내 AWS 로그인(Identity Center)을 쓰는 조직. 스택 C 가 필요 없습니다.

### ⑤ 사내망 전용 — S3 인터페이스 엔드포인트 + 버킷 정책 · 고객 구성 · 제품 밖

- **무엇**: 고객이 S3 인터페이스 VPC 엔드포인트를 두고, 버킷 정책에 「그 엔드포인트(`aws:SourceVpce`)를 거치지 않은 요청은 거부」를
  더합니다. 사내(VPN · Direct Connect)에서만 받거나 열 수 있게 됩니다. **제품 쪽에서 구성 · 검증하지 않았습니다.** 아래는 템플릿을
  근거로 한 주의점입니다.
- **버킷 전체를 막으면 수집이 멈춥니다.** 이 버킷에 쓰는 주체는 전부 고객 VPC 밖(공용 S3 엔드포인트)에서 옵니다 — 스택 A 의
  CodeBuild · Lambda 에는 VPC 설정이 없습니다. 막으면 안 되는 주체: 수집 역할(`BuildRole`) · 모니터링 역할(`StateRole`) · 서명 역할
  (`SignerRole`) · (스택 C 를 쓰면) CloudFront.
- **서명 역할을 주체 이름으로 통째로 빼면 사내망 제한이 무너집니다.** 화면 안 서명 주소는 서명 역할의 이름으로 처리되므로(§0),
  그 역할을 예외로 두면 파일을 가진 **사내망 밖의 누구나**도 예외가 됩니다. 예외는 「주체」가 아니라 「키 + 동작」으로 갈라야 합니다:
  브라우저가 하는 일 = `state-latest.json` 읽기 · `control/desired.json` 쓰기 · `index.html` 읽기, 서명 함수 자신이 하는 일 =
  `unsigned/index.html` 읽기 · `index.html` 쓰기. 겹치지 않으므로 앞의 세 가지에만 엔드포인트 조건을 거는 설계가 **가능해 보이지만
  검증하지 않았습니다.**
- **스택 C 와 함께 쓸 수 없습니다.** CloudFront 는 공용 엔드포인트로 버킷을 읽습니다. CloudFront 를 예외로 두면 링크가 인터넷에서 열립니다.
- 사내 브라우저가 `<버킷>.s3.<리전>.amazonaws.com` 을 엔드포인트로 보내려면 엔드포인트의 프라이빗 DNS 와 사내 DNS 전달이 필요합니다
  (AWS 문서 기준). 주소의 호스트를 바꾸면 서명이 깨집니다.
- **망이 지키는 것은 「받기 · 실시간」이지 파일 내용이 아닙니다.** 사내에서 받은 파일은 노트북에 실려 밖으로 나갈 수 있습니다(§0-1).
- **맞는 경우**: 외부에서 닿는 것 자체를 금지해야 하는 조직. 설계 · 검증은 고객 몫입니다.

## 3. 실시간 숫자는 CloudFront 를 거치지 않는다 — 커스텀 도메인은 스택 A `ViewerOrigin` 에 적는다

- 화면은 상태 읽기와 신호 쓰기를 **화면 안의 S3 서명 주소로 직접** 부릅니다. 스택 C 는 `index.html` 한 번만 내줍니다.
  검증 결과: 실시간 요청은 전부 S3 리전 오리진으로 직접 가고, CloudFront 로는 `index.html` 1회만 갑니다.
- 그래서 다른 오리진에서 연 화면은 S3 의 CORS 허용을 받아야 합니다. 허용 목록은 `"null"`(내려받아 `file://` 로 연 화면)과
  원본 하나입니다. 원본은 기본이 `https://*.cloudfront.net`(스택 C 기본 도메인)이고, 스택 A `ViewerOrigin` 을 주면 그 값 하나로
  바뀝니다(`infra/stack-a-collector.yaml` 의 `ArtifactBucket` CORS).
- 스택 C 에 커스텀 도메인을 붙이면(`CustomDomainName`) 화면 오리진이 그 도메인이 됩니다. 스택 A `ViewerOrigin` 을
  `https://<커스텀 도메인>` 으로 두면 실시간 숫자도 그대로 옵니다. 비워 두면 CORS 목록에 없으므로 **그림은 뜨고 실시간 숫자는
  막힙니다.** `ViewerOrigin` 은 원본을 하나만 받으므로, 커스텀 도메인을 적으면 `*.cloudfront.net` 기본 도메인으로 연 화면의 숫자가
  대신 막힙니다. 템플릿 파라미터 설명에도 적혀 있습니다.
- 판정 근거는 **코드**(CORS 목록 + 화면의 직접 요청)입니다. 커스텀 도메인을 실제로 붙여 재지는 않았습니다.
- CORS 는 권한을 주지 않습니다 — 서명 없는 요청은 오리진과 무관하게 403 입니다.

## 4. 스택 C 비밀키 다루기

비밀키 한 장 = **수명 제한 없는 열람 링크를 얼마든지 만들 수 있는 권한**입니다(§2 ③ 수명). 그렇게 다룹니다.

**어디에 두나**

- 관리자 PC 에서 만들고 **AWS 에 올리지 않습니다** — 설계 결정입니다. 스택에는 공개키만 들어갑니다. `deploy.sh` 는 비밀키를
  `out/viewer-k1.pem`(권한 600)에 만듭니다.
- 키를 가진 사람은 1~2명으로 한정합니다.
- **CloudShell 에서 만들었다면** CloudShell 홈 폴더는 세션이 끝나도 AWS 관리 저장소에 남습니다(AWS 문서 기준). 서명 뒤 지우거나,
  처음부터 관리자 PC 에서 만듭니다.
- **백업은 필수가 아닙니다.** 키를 잃으면 새 키로 교체하면 됩니다(아래). 대가는 옛 링크가 무효가 되어 다시 나눠 줘야 한다는 것뿐입니다.
  조직 규정이 키 보관을 요구하면 사내 비밀 보관소를 씁니다.

**교체 두 가지** — CloudFront 는 올린 공개키 값을 바꿀 수 없으므로 키 자리 둘(`k1` · `k2`)을 번갈아 씁니다. 교체 뒤 링크의
`Key-Pair-Id` 가 바뀝니다.

- **계획된 교체(겹침)** — `./deploy.sh --viewer --rotate-key --days N`. 새 키를 빈 자리에 넣고 옛 키는 키 그룹에 남깁니다(스택 C
  `PreviousPublicKeyPem`). 옛 링크는 만료될 때까지 열리고, 새 링크는 새 키로 나갑니다. 옛 링크가 다 만료되면
  `./deploy.sh --viewer --retire-old-key` 로 옛 키를 뺍니다. 스크립트는 이 PC 의 발급 기록(`~/.local/state/nettopo/viewer-links.log`,
  링크 · 서명은 기록하지 않음)에서 옛 키로 낸 링크의 가장 늦은 만료를 알려 줍니다.
- **유출 대응(즉시)** — `./deploy.sh --viewer --rotate-key --no-overlap --days N`. 같은 갱신에서 옛 키를 빼므로 지금까지 낸 링크가
  **전부** 403 이 됩니다. 검증 결과: 교체 완료 직후 옛 7일 · 10년 링크 403, 새 링크 200, 스택 갱신은 30초 남짓.

**교체가 무효로 하지 못하는 것**

- 이미 열어 둔 화면, 이미 저장한 화면 파일(§0-1).
- 그 화면 안의 S3 서명 주소(최대 약 12시간) — 서명 함수 역할의 서명이라 CloudFront 키와 무관합니다(§0-2).
- ② 의 S3 서명 URL, ① · ④ 로 받은 파일.

**언제 교체하나 (권장)** — 유출이 의심될 때 즉시(겹침 없이). 그리고 링크를 받은 사람 무리가 바뀔 때(퇴사 · 외부 협력사 종료).
링크 하나만 끊을 수 없으므로 「무리가 바뀌면 교체 + 남은 사람에게 재발급」이 유일한 회수 방법입니다. 링크 수명은 짧게(예: 30일)
잡고 액세스 로그 보존 기간과 함께 정합니다 — 운영 권장이고 제품 기본값이 아닙니다.

**서명 방식** — 스크립트는 RSA 2048 키와 **SHA-256** 으로 CloudFront 서명 URL 을 만들고, 링크에 `Hash-Algorithm=SHA256` 을 붙입니다
(`infra/issue-viewer-link.sh`). 이 값이 빠지면 CloudFront 는 SHA-1 로 검증해 403 을 냅니다.

## 5. 이 제품의 범위 밖

- **CloudFront 앞 로그인층**(Cognito + Lambda@Edge 등), ALB + OIDC, Amplify 접근 제어, WAF IP 제한, 수집 뒤 메신저 · 메일 밀어 넣기 —
  이 제품은 이들을 만들지도 시험하지도 않습니다. 고객이 자기 판단으로 스택 C 위에 얹을 수 있으나 제품이 권하지 않으며 동작을
  보장하지 않습니다.
- 이런 층은 흔히 커스텀 도메인과 같이 오는데, 그 경우 §3 대로 스택 A `ViewerOrigin` 에 그 도메인을 적어야 실시간 숫자가 옵니다.

## 6. 고르는 법 — 보는 사람이 누구인가로 정한다

| 보는 사람 | 권장 | 이유 |
|---|---|---|
| 모니터링 계정에 로그인하는 관리자 몇 명 | ① 내려받기 | 추가 구성 0 |
| 전원이 사내 AWS 로그인(Identity Center)을 쓴다 | ④ 권한 세트 + 데이터 이벤트 | **누가 받았는지 이름이 남는 유일한 길**. 스택 C 불필요 |
| AWS 계정이 없는 사람, 몇 시간만 | ② 서명 URL | 추가 구성 0, 스스로 만료 |
| AWS 계정이 없는 사람, 오래, 개인 식별 불필요 | ③ 스택 C | 링크가 열 때마다 최신 화면을 준다. 로그를 읽을 사람을 좁히고 키를 §4 대로 다룬다 |
| 외부에서 닿는 것 자체가 금지 | ⑤ 사내망 전용 | 고객 설계. §2 ⑤ 주의점을 먼저 본다. 스택 C 와 함께 못 쓴다 |

모든 길에서 공통: 받은 파일은 회수할 수 없고, 모니터링을 켠 스택이면 파일 안에 최대 약 12시간짜리 서명 주소 4개가 있습니다(§0).

## 7. 제품 쪽에서 확인하지 않은 것

1. 화면 안 서명 주소의 실효 수명(설계상 최대 12시간 · 서명 함수 자격 증명 수명에 따라 더 짧을 수 있음).
2. ② (나) 관리자 발급 서명 URL 로 연 화면에서의 실시간 동작.
3. 서명 함수 역할의 세션을 끊은 뒤 서명 함수가 새 자격 증명으로 다시 서명하는지.
4. ④ 권한 세트 구성과 S3 콘솔 열기, 데이터 이벤트에 남는 이름.
5. ⑤ 사내망 전용 버킷 정책 전체(수집을 멈추지 않는 조건 설계 포함).
6. 커스텀 도메인에서 `ViewerOrigin` 을 주면 실시간이 실제로 오고, 비우면 막히는 것(§3 은 코드 근거).
7. S3 서버 액세스 로그 · CloudTrail 에 서명 문자열이 어떻게 남는지, 메신저 미리보기 봇의 접근.
